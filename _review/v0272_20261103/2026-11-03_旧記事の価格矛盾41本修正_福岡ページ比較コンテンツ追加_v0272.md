## 2. 【事実】公開ページは Firestore を優先して読んでいる

`blog/index.php` を読んで確認しました。

```php
// 詳細ページ（/blog/?id=xxx）
$post = news_find($blog_id);                              // ① Firestore
if (!$post) $post = blog_seed_find($blog_id);             // ② data/news.json
if (!$post) $post = blog_archive_find($blog_id);          // ③ data/blog-posts.json

// 一覧ページ（/blog/）
foreach (news_published() as $it) $push($it);             // ① Firestore（IDが先着優先）
foreach (($seed['items'] ?? []) as $it) $push($it);       // ② data/news.json
foreach (blog_archive_items() as $it) $push($it);         // ③ data/blog-posts.json
```

`$push()` は `if (isset($seen_ids[$id])) return;` で**同じIDは先に入ったほう（＝Firestore）だけを残します**。

一方 `admin/migrate-blog.php` は

```php
if (!$force) {
  $exists = news_find($id);
  if ($exists) { $skip++; continue; }   // 既存IDはスキップ
}
```

つまり **「JSONを直す → migrate を実行」では、既存の旧記事は1件も更新されません。**

これは今まで見落としていました。v0270の報告で「旧記事18本の価格矛盾」を挙げたとき、JSONを直せば直ると書きましたが、それは誤りでした。訂正します。

### 4-2. 【仮説】

「福岡 墓じまい」は**比較・選び方のクエリ**です。1位が「5選」記事なのはそのためで、検索者は「どこに頼むか決めたい」状態です。自社1社の説明しか載っていないページは、どれだけ内容が良くても**その意図に答えていません**。

### 4-5. ダメ出し検証：この案が失敗するとしたら何が原因か

1. **一番ありうる失敗：Googleが「このクエリにはポータルを出す」と決めている。** 「おすすめ○選」型のクエリは、事業者単体のページをどうやっても1位に置かないことがあります。この場合、1位は構造的に取れません。
   → その場合の代替ルートは**下の「別ルート」**に書きます。
2. **比較表が薄いと逆効果。** 4タイプの違いが当たり障りのない説明に見えると、滞在が伸びず順位も動きません。各タイプの「確認しておきたい点」に具体性があるかが分かれ目です。今回は「窓口と施工者が分かれる」「撤去は外注になる」といった実務の話にしましたが、もし順位が動かなければここを実例ベースに書き替えるのが次の手です。
3. **ページが長くなりすぎて問い合わせが減る。** 比較セクションは「決める前の情報」なので、読み終わる前に離脱させる可能性があります。追加位置を施工事例の後（＝証拠を見せたあと）にしたのはこのためですが、問い合わせ数が落ちたら位置を下げます。**これはGA4の問い合わせ数で2週間後に見ます。**
4. **「2026年11月3日」の更新日が固定値なので、放置すると半年後に「古い」と見える。** 今後ページを触ったら必ず `$page_updated` を直す必要があります。これは運用の約束事として残ります。

### 4-6. 別ルート（上記1が起きた場合）

1位をポータルが占めているなら、**勝ち筋はそのクエリの1位ではなく、ロングテールの総量**に切り替えます。すでに `福岡市 墓じまい`（13.4位）`福岡 改葬許可`『福岡 市営墓地 返還』のような具体クエリの記事は v0271 で80本入れています。そちらの合計クリックを取りにいき、「福岡 墓じまい」は2位で確保しておく、という形です。この判断は2〜3か月後のGSCで切り替えます。
