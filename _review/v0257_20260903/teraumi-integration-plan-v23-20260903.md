## §A. 適用スキルと優先順位

### A-1. 判断の優先順位（全工程で厳守）

```
1. 今回の仕様書・実在する事実・制約
2. en1150.co.jp の既存構造・役割分担・既存SEO資産
3. 登録済みスキル
4. Claude独自の追加提案
```

**運用ルール**：スキルの一般論を理由に、既存URL・料金・実績・ブランド構造・既存SEO評価を変更しません。スキルの推奨と今回の仕様が矛盾した場合は、**必ず仕様を採り、その旨を本書に明記します**（実例は A-3）。

### 2-3. 「迷わせない」ための3つの仕掛け

## 9.【提出物7】旧URL → 新URL 301対応表

### 9-1. 転送方式：4パターンすべてから直接1ホップを第一候補にする

**目標はこの形です。**

```
http://teraumi.com/plans.php          ─┐
https://teraumi.com/plans.php          ├→ 301（1ホップ）→ https://en1150.co.jp/teraumi/#price
http://www.teraumi.com/plans.php       │
https://www.teraumi.com/plans.php     ─┘
```

224本すべてを、**4パターン（http / https × www有 / www無）から直接、対応する新URLへ1ホップ**で飛ばします。中継を挟まないほうが評価の引き継ぎが確実で、クロール効率も落ちません。

#### 第一候補：Cloudflare（推奨）

en1150.co.jp で既に運用しており、追加コストなしで実現できます。

| 手順 | 内容 |
|---|---|
| 1 | teraumi.com のネームサーバーを Cloudflare へ変更（レジストラでの作業。**要確認事項 #2 のドメイン管理権限が前提**） |
| 2 | DNSに `teraumi.com`（apex）と `www` の2レコードを作り、**両方をプロキシ有効（オレンジ雲）**にする。転送するだけなので向き先はダミーIPで構わない |
| 3 | Universal SSL が apex と www の両方をカバーするので、https の4パターンを受けられる |
| 4 | **Bulk Redirects** に224行のリストをアップロード（1対1の転送表がそのまま使えます）。パターンが単純なものは Redirect Rules でまとめる |
| 5 | **「Always Use HTTPS」は有効にしない。** これを有効にすると `http://` のリクエストがまず `https://` へ1回301され、そのあと転送先へもう1回301＝2ホップになります。無効のままなら http のリクエストにも Redirect Rules が直接応答できます |

> ⚠️ **ここは実測で確認します。** Cloudflareの処理順序（Always Use HTTPS と Redirect Rules のどちらが先か）は設定と製品仕様に依存します。設定後に **224URL × 4パターン＝896本**のステータスを実測し、1ホップになっていることを確認します。**もし http だけ2ホップになる場合は、その事実を記録したうえで http のみ2ホップを許容**します（https・www有無は1ホップを維持）。

#### 第二候補：現サーバーの `.htaccess`

Cloudflareへ移せない場合はこちらです。**1ホップで書けるかは現行のvhost構成に依存**します。

| 条件 | 1ホップで書けるか |
|---|---|
| `teraumi.com` と `www.teraumi.com` が同一vhostで受けられている | ✅ 可能。`RewriteRule` で直接 en1150 へ |
| http と https が同一vhost・同一 `.htaccess` を通る | ✅ 可能 |
| 上位（ロードバランサ・サーバー設定）で http→https が強制されている | ❌ http のみ2ホップ |
| www有無で別vhost・別証明書 | ❌ 片方が2ホップ |

書き方の方針：`RewriteCond %{HTTP_HOST}` で www 有無を問わず受け、`RewriteRule` は**リクエストのプロトコルを見ずに**直接 `https://en1150.co.jp/...` へ `[R=301,L]` で飛ばします。**`RewriteCond %{HTTPS} off` で https へ寄せる行を書かない**のがポイントです（それを書くと2ホップになります）。

#### 2ホップを許容する条件（例外）

次のいずれかに該当する経路**だけ**、2ホップを許容します。**許容した場合は、どのパターンがなぜ2ホップになったかを実測結果に記録し、ご報告します。**

1. サーバー側またはCDN側で http→https が上位で強制されており、無効化できない
2. www有無が別サーバー・別証明書で運用されており、片方を統合できない
3. Cloudflare を使えず、かつ現サーバーの `.htaccess` を編集できない（この場合はそもそも転送自体が成立しないため、§24 #1 の確認が最優先）

## 26. 設計の説明（仕様§31の後半への回答）

### なぜこの設計にしたのか

teraumi.com は**すでに縁のサイト**でした。会社概要も代表者も問い合わせ先メールも同一で、ルートページから en1150.co.jp へ11本リンクしています。つまり今回やるべきことは「他社を吸収する」ことではなく、**2つに分かれていた自社の情報を1つに戻す**ことです。

だから新規ページは `/teraumi/` **1本だけ**にしました。旧サイトの9ページ分は、この1ページと既存ページに畳み込みます。ページを増やせば増やすほど「サービスが増えた会社」に見え、内部リンクも薄まります。仕様§14の「サービスが増えた、ではなく、希望に合わせて組み合わせられる」を実現する最短の形が、**ページを増やさないこと**でした。

`SERVICES` 定数への1行追加という実装を選んだのも同じ理由です。ナビ・フッター・フォーム・sitemap・構造化データの5か所に同時に反映されるため、teraumiだけが特別扱いされる余地がコード上に生まれません。**「体系の中の1つ」であることを、実装の構造そのもので担保しています。**

### ユーザーを迷わせないために何をしたか

3つです。

**1つ目は、teraumiを新しい選択肢として並べなかったこと。** `/kaiyou-sou/` と `/kaiyou-sou/fukuoka/` には既に「すべてを海に還さなくても、かまいません」というセクションがあり、手元供養とメモリアルジュエリーの2枚が並んでいます。teraumiはその**3枚目**として入れます。ユーザーから見ると新サービスの登場ではなく、**いま読んでいた話の続き**です。

**2つ目は、診断で「すべて還したい」人にteraumiを見せないこと。** 質問は1問しか増やしません。しかもその1問は「一部は残したい」を選んだ人にしか出ません。仕様§4が指定する「teraumiが不要な方」の線引きを、文章ではなく**表示ロジックで**守ります。読んでもらう努力より、そもそも見せないほうが確実です。

**3つ目は、通常の海洋散骨を1文も否定しないこと。** 旧サイトの中心的な訴求は「散骨すると手を合わせる場所がなくなる」という論法でした。これは仕様§3で禁止されていますし、そもそも縁の既存の海洋散骨ページの価値を自分で削る主張です。`/teraumi/` の「違い」セクションは比較表にせず、**向いている人の並列表**にして、通常の海洋散骨の列に「海そのものが、手を合わせる場所になります」と明記します。

### teraumiが問い合わせのボトルネックにならないために何をしたか

270,000円は委託海洋葬（54,450円）の**約5倍**です。ここが最大のリスクだと考えています。

対策は4つ。**料金をFVに出さない**（迷いから入る）。**料金セクションの直後に予算別の代替案を置く**（委託海洋葬54,450円〜＋分骨5,500円＝**59,950円〜**への逃げ道を必ず用意する。金額は丸めない）。**主CTAを申込ではなく相談にする**。そして**GA4で「通常の海洋散骨ページのCV率」を統合前後で比較できるようにし、10%以上下がったらteraumiの露出を段階的に弱める**という撤退ラインをあらかじめ決めておくことです。

teraumiは選択肢の1つであって、主力のCVを削ってまで押す対象ではありません。**下げられる設計**にしておくことが、いちばん確実なボトルネック対策だと考えました。

### teraumi.com のSEO・被リンク資産をどう引き継ぐのか

**301を1対1で、1ホップで通す**のが基本です。224URLすべてに転送先を決め、**http / https × www有無の4パターンすべてから直接**飛ばします（§9-1）。中継を挟まないほうが評価の引き継ぎが確実だからです。Cloudflare を第一候補にするのは、en1150 で既に運用していて追加コストがなく、**「Always Use HTTPS」を有効にしないことで http のリクエストにも直接301を返せる**ためです。ただしここは設定後に896本を実測して確かめます。記事57本は分類ごとに転送先を変え（A→新記事、B→統合先、C→本体のアンカー、D→本体トップ）、タグのうち検索意図が明確な7本も個別に振り分けています。一括転送で済ませないのは、**内容が近いURLへ送るほど評価が引き継がれる**からです。

そして**ドメインを手放さない**こと。これが最大の被リンク対策です。301が生きている限り評価は移り続けます。

被リンクについては正直にお伝えしますが、**バックアップからは分かりません**。分かったのは「teraumi が外部へ張っていたリンク」＝掲載された媒体です。実測にはGSCかAhrefsが要ります。そのうえで、依頼の優先順位は**PR TIMES → 提携先28か所 → 日本海洋散骨協会 → 報道各社**としました。PR TIMESが自社配信で変更可能性が高く、転載先が多いためです。提携寺院への連絡は統合の周知としても必要なので、リンク変更依頼と同時に行うのが効率的です。

### 登録済みスキルをどう活用したか

11のスキルを、章ごとに具体的なルールとして落としました（対応表は §A-2）。特に効いたのは4つです。

**master-orchestrator の「完成度が高い部分は触らない」**。既存の `#bunkotsu`・`/shindan/` の決定木・`SERVICES` 定数は、すでによくできた資産でした。だから作り直さず、**3枚目のカード・1問の追加・1行の追加**という形に収めました。新規ページ1本・新規CSSゼロ・新規GA4イベントゼロという差分の小ささは、この判断から出ています。

**web-marketing-analysis の「ボトルネックを1つ特定する」**。施策を並べる前に、今回いちばん売上を止めうる要因を1つに絞りました。答えは「270,000円という価格の見せ方」です。§5-4 の対策4つと §23 の撤退ラインは、すべてこの1点への対処です。

**seo-llmo の Entity SEO と AEO**。teraumi用に新しい Organization ノードを作らず、既存の `#organization` を `@id` で参照するだけにしました。**別法人だとAIに誤解させないための最重要ポイント**です。見出しは疑問形にして直後に1〜2文で答え切る形にしました。

**meo-local の NAP統一**。「1文字も違わせない」という原則で突合したところ、旧サイトの「坂之上7-7-3」と en1150 の「坂之上7丁目7-3」の表記ゆれが見つかりました。統合前に潰します。

一方で、スキルの一般論が今回の仕様と矛盾した箇所が5つありました（§A-3）。**すべて仕様を優先し、その記録を本書に残しています。**「トップに新サービスカードを置く」「専用LPを作る」「サービス単位でGBPを分ける」「FVに価格を出す」「記事は全部残す」——どれも一般論としては正しいのですが、今回は採用していません。

### GEO / MEO / LLMO までどう一貫させたのか

**同じ事実を、4つの場所に同じ言葉で置きます。**

`/teraumi/#temples` に書く「提携先11都府県・28か所」「散骨海域15か所」「鹿児島本社・福岡営業所」という事実を、そのまま `llms.txt` の新設節に、`Service` 構造化データの `areaServed` に、GBPのサービス項目に反映します。NAPは「坂之上7丁目7-3」表記に統一します（旧サイトの「坂之上7-7-3」表記との揺れを解消）。

AI検索向けには、**4つの供養方法の違いを `llms.txt` に明示的に定義**します。「海洋散骨のみ／＋手元供養／＋寺院納骨（teraumi）／寺院納骨のみ」を、それぞれ料金と条件つきで書き分けます。AIが取り違えやすいのはここだからです。本文も「全国対応しています」のような主語のない文を避け、「有限会社 縁は、〜を提供しています」という主語述語のある文で書きます。**人が読んでも、AIが読んでも、同じ意味に取れる文章**にします。

MEOでは teraumi 専用のGBPを作りません（仕様§22）。作れば「別ブランド」というシグナルをGoogleに送ることになり、SEO・GEO・LLMOでやろうとしている統合と矛盾します。既存2拠点のGBPにサービス項目を1つ足すだけにします。
