# 管理画面に今回の24記事が出ない理由と、取り込み手順

作成：2026-09-26 ／ 対象：en1150（有限会社 縁）／ 現象：管理画面が 255件のまま

---

## 0. 結論

**設計どおりです。管理画面は Firestore だけを読んでいるため、JSONに追加した記事は出ません。**

そして**解決策はすでにリポジトリの中にあります。** `/admin/migrate-blog.php` を1回実行するだけです。
デプロイを済ませたあとに実行すれば、管理画面は **255 → 279件** になります。

---

## 1. 原因（コードで確認）

| 画面 | 読んでいるデータ |
|---|---|
| **管理画面** `admin/news/index.php` | `news_all()` ＝ **Firestore の `news` コレクションのみ** |
| **公開ページ** `/blog/index.php` | Firestore ＋ `data/news.json` ＋ `data/blog-posts.json` を統合 |
| **TOP** `index.php` の新着 | 同上（統合） |

```php
// admin/includes/store.php
function news_all(): array {
  $items = [];
  foreach (fs_list_all(NEWS_COLLECTION) as $doc) $items[] = fs_from_doc($doc);  // Firestoreのみ
  return $items;
}
```

今回の24記事は `data/blog-posts.json` に追加したため、**公開ページには出ますが、管理画面には出ません。**

### 件数が完全に一致しています

| | 件数 |
|---|---|
| `data/blog-posts.json`（今回の追加前） | **255件** |
| 管理画面の表示 | **255件** |
| `data/blog-posts.json`（追加後） | **279件** |

Firestore の中身は `blog-posts.json` の追加前の内容と1件単位で一致しています。
つまり**過去に一度 migrate-blog.php で取り込まれた状態**で、それ以降 JSON に追加された分だけがずれている、という状態です。

---

## 2. 解決策 — `/admin/migrate-blog.php`

リポジトリに専用の取り込みツールが既にあります（`admin/migrate-blog.php`／v20260713-0110）。

**このツールの挙動**

- `data/blog-posts.json` を読み、Firestore の `news` へ `news_upsert()` する
- **既に同じIDがFirestoreにある記事はスキップ**する（管理画面で編集済みの記事を守る設計）
- 50件ずつ処理し、3秒後に自動で次へ進む
- 完了後に `en_cache_bust('news_published')` が走るため、公開側のキャッシュ（TTL 900秒）も即時クリアされる

**今回のケースでの結果予測**

- 279件を走査 → 既存255件はスキップ → **新規24件だけが登録される**
- 6回の自動継続（50×5＋29）でおよそ20〜30秒
- 管理画面：255 → **279件**

## 3. 実行手順（順序が重要）

### ⚠ 先にデプロイを完了させてください

`migrate-blog.php` は**本番サーバー上の** `data/blog-posts.json` を読みます。
デプロイ前に実行しても、本番のJSONは255件のままなので**24件は入りません。**

```
1. git push origin main
2. Cloud Build 完了を待つ
3. 本番の版数が v20260713-0264 になったことを確認
4. ← ここで初めて migrate-blog.php を実行
```

### 実行

1. 管理画面にログインする（`https://en1150.co.jp/admin/`）
2. 次のURLを開く

```powershell
Start-Process "https://en1150.co.jp/admin/migrate-blog.php"
```

3. 「アーカイブ記事 **279件** を Firestore に取り込みます」と表示されることを確認
   → **255件と表示されたらデプロイが届いていません。** 戻ってビルドを確認してください
4. 「取り込みを開始する」をクリック
5. 自動で最後まで進みます（ページを閉じると止まります）
6. 「すべての取り込みが完了しました」が出たら終了

### 確認

- 一覧の最上部に 2026-09-26 の記事（おひとりさまの終活／兄弟で意見が合わない／分骨証明書／寺院納骨の供養年数）が並ぶ
- 各記事の「編集」から本文が開ける（＝堤様が自分で直せる状態になる）

## 4. 実行しなかった場合どうなるか

公開ページには24記事が出ます。ただし：

- **堤様が管理画面から編集・削除できません**
- 誤字や価格改定のたびに、こちら側でJSONを直してデプロイする必要があります
- 同じタイトルで管理画面から新規作成されると、JSON側とFirestore側で二重になります（IDが違うため重複排除が効きません）

**運用を堤様に渡す前提なら、取り込みは必須です。**

## 6. ダメ出し検証（この手順が失敗するとしたら）

- **失敗要因①**：デプロイ前に実行してしまい「255件」で完了してしまう。
  → 実行前に確認画面の件数が **279件** であることを必ず見てください。ここが唯一の関門です。

- **失敗要因②**：Firestore の書き込みクォータ、または権限エラーで失敗する。
  → 画面に「NG: <id>」がログ表示されます。失敗したIDが出た場合は、同じURLを再実行すれば成功分はスキップされ、失敗分だけ再試行されます。

- **失敗要因③**：途中でページを閉じてしまい、一部しか入らない。
  → 再実行すれば既存分はスキップされるので、何度実行しても安全です（`force=1` を付けない限り上書きしません）。

- **失敗要因④**：`?force=1` を付けて実行してしまい、**管理画面で手直しした既存記事がJSONの内容で上書きされる。**
  → `force=1` は付けないでください。今回は不要です。

- **失敗要因⑤**：取り込み後も公開側の表示が変わらない。
  → Firestore側が優先表示される設計のため、見た目は変わりません（同じIDなので同じ内容）。これは正常です。

## 7. 今後の運用をどうするか（要判断）

記事追加の経路が2つあると、今回と同じずれが繰り返されます。

| 案 | 内容 | 向いている場面 |
|---|---|---|
| **A（推奨）** | まとめて作るときは JSON → `migrate-blog.php` で取り込む、を**1セットの手順とする** | こちら側で大量に書くとき |
| B | 管理画面から1件ずつ作る | 堤様が自分で書くとき |
| C | JSONシードを廃止し、Firestoreのみを正とする | 将来的な整理。ただし `blog-posts.json` は障害時のフォールバックにもなっているため、外すかどうかは別途判断 |

**A を標準手順として、今回のデプロイ手順書にも追記しました。**
