# en1150｜Cloud Run へ直接デプロイする方法

作成：2026-09-15
対象：`D:\__github_win\en-lp\push\en-lp` → Cloud Run サービス `en-lp`（asia-northeast1）
目的：GitHub への push を経由せず、ローカルの現ファイルをそのまま本番へ反映する

---

## 0. 先に読んでください（この方法の最大のリスク）

**直接デプロイは git を経由しません。本番とGitHubの内容が乖離します。**

その状態で誰か（syu／Codex／GitHub Desktop）が `git push` すると、Cloud Build が走って
**直接デプロイした内容が古いリポジトリの内容で上書きされ、消えます。**

対策は1つだけです。

> **直接デプロイしたら、その日のうちに必ず同じ内容を commit して push する。**

「デプロイ＝完了」ではなく「デプロイ → 動作確認 → commit & push」までが1セットです。
この順序を守れば、直接デプロイは「本番で先に確認してから履歴に残す」安全な使い方になります。

## 3. 方法A：`gcloud builds submit`（**推奨**）

既存の `cloudbuild.yaml` をそのまま使うため、**リビジョン設定が現行と完全に同一**になります。
ビルド環境も Cloud Build（E2_HIGHCPU_8）で、GitHub 経由と同じです。

```powershell
cd D:\__github_win\en-lp\push\en-lp

gcloud builds submit `
  --config=cloudbuild.yaml `
  --substitutions=SHORT_SHA=manual20260915a
```

### `SHORT_SHA` を必ず指定する理由

`cloudbuild.yaml` はイメージタグに `${SHORT_SHA}` を使っています。
`SHORT_SHA` は GitHub トリガー経由でしか自動で入らず、**手動実行では指定しないと空文字になります。**
その場合タグが `en-lp:` となり、ビルドが壊れます（エラーにならず静かに失敗する形）。

Google Cloud の公式ドキュメントでは、`gcloud builds submit --substitutions` で指定できる組み込み変数として
`REPO_NAME` `BRANCH_NAME` `TAG_NAME` `REVISION_ID` `COMMIT_SHA` `SHORT_SHA` が明記されています。
`PROJECT_ID` と `BUILD_ID` は上書きできません（`PROJECT_ID` は自動で入るので指定不要）。

### タグの付け方

あとから「どのビルドが本番か」を追えるように、日付＋連番にしてください。

```
manual20260915a  →  同日2回目は manual20260915b
```

git のコミットハッシュと混ざらないよう、頭に `manual` を付けるのが安全です。

### アップロード対象について

`gcloud builds submit` はカレントディレクトリの内容を Cloud Build へ送ります。
`.gcloudignore` が無い場合は `.gitignore` を元に除外が決まります。
確実にしたい場合は、`.dockerignore` と同じ内容で `.gcloudignore` を置いてください（任意）。

## 4. 方法B：`gcloud run deploy --source .`（最短だが差異あり）

```powershell
cd D:\__github_win\en-lp\push\en-lp

gcloud run deploy en-lp `
  --source . `
  --region=asia-northeast1
```

カレントに `Dockerfile` があるため、**buildpacks ではなく既存の Dockerfile が使われます**（公式ドキュメントで確認済み）。

### ただし、現行と2点ちがいます

| | 方法A（builds submit） | 方法B（run deploy --source） |
|---|---|---|
| イメージの置き場所 | `asia-northeast1-docker.pkg.dev/<PROJECT>/**en-lp**/en-lp:<タグ>` | `.../**cloud-run-source-deploy**/...`（リポジトリが自動作成される） |
| `cloudbuild.yaml` | 使う（memory/cpu/concurrency等が明示適用） | **使わない**（既存リビジョンの設定を引き継ぐ） |
| `APP_VERSION` 環境変数 | 毎回タグで更新 | **更新されない**（古い値が残る） |

イメージが2つのリポジトリに分散するため、あとで「どれが本番か」が分かりにくくなります。
**常用するなら方法A、緊急の1回だけなら方法B**、という使い分けが安全です。

なお `APP_VERSION` 環境変数がサイト側で使われているかは**未確認**です。
PHP側のバージョン表示は `includes/config.php` の `const APP_VERSION` を見ているため、
環境変数が古くても表示には影響しない可能性が高いですが、確認してから常用判断をしてください。

## 5. 方法C：ローカルで docker build（Docker Desktop が要る）

Cloud Build を使わず、手元でイメージを作って push します。ビルド課金は発生しませんが、Docker Desktop が必要です。

```powershell
cd D:\__github_win\en-lp\push\en-lp

$PROJ = gcloud config get-value project
$TAG  = "manual20260915a"
$IMG  = "asia-northeast1-docker.pkg.dev/$PROJ/en-lp/en-lp:$TAG"

gcloud auth configure-docker asia-northeast1-docker.pkg.dev

docker build -t $IMG .
docker push $IMG

gcloud run deploy en-lp `
  --image=$IMG `
  --region=asia-northeast1 `
  --platform=managed `
  --allow-unauthenticated `
  --port=8080 --memory=256Mi --cpu=1 `
  --min-instances=0 --max-instances=10 `
  --concurrency=80 --timeout=60s `
  --set-env-vars=APP_VERSION=$TAG
```

Windows の Docker Desktop はメモリを食うため、頻繁に使わないなら方法Aで十分です。

## 7. 切り戻し（ロールバック）

新しいリビジョンに問題があったら、前のリビジョンへトラフィックを戻します。**再ビルド不要・数十秒で戻ります。**

```powershell
# リビジョン一覧
gcloud run revisions list --service=en-lp --region=asia-northeast1 --limit=5

# 戻す
gcloud run services update-traffic en-lp `
  --region=asia-northeast1 `
  --to-revisions=<戻したいリビジョン名>=100
```

直接デプロイを使うなら、**実行前に現在のリビジョン名を控えておいてください。**

```powershell
gcloud run services describe en-lp --region=asia-northeast1 --format="value(status.latestReadyRevisionName)"
```

## 8. Worker は別系統（忘れやすい）

Cloud Run のデプロイでは **Cloudflare Worker は更新されません。**
今回の v0263 では `worker/en-contact/worker.js` も変更しているため、こちらも必要です。

```powershell
cd D:\__github_win\en-lp\push\en-lp\worker\en-contact
npx wrangler deploy
```

これを飛ばすと、LPは `gclid`/`utm_*` を送るのに Worker が転送せず、**広告情報がDBに保存されません。**

## 9. 今回（v0263）の実行順

| 順 | 内容 | コマンド |
|---|---|---|
| 1 | 現在のリビジョン名を控える | 7章 |
| 2 | サイトをデプロイ | 3章（方法A） |
| 3 | Worker をデプロイ | 8章 |
| 4 | 本番確認 | 6章 |
| 5 | 送信テスト1件（`mk@lu-m.co.jp`／【テスト送信】明記） | — |
| 6 | **commit & push**（乖離を解消） | 下記 |

```powershell
cd D:\__github_win\en-lp\push\en-lp
git --no-optional-locks status --short
git add lp1/index.php lp1/script.js lp1/styles.css api/inquiry-log.php admin/inquiries/index.php includes/config.php VERSION
git commit -m "lp1: contact_submit計測・広告識別子保存・合同散骨日程の一元化 (v20260713-0263)"
git push origin main
```

⚠ push すると Cloud Build が走り、**もう一度デプロイされます**（内容は同じなので実害はありません）。
これを避けたい場合は、先に commit & push だけ行って Cloud Build に任せる、という選択もあります。
つまり **「直接デプロイ」が本当に必要なのは、push できない事情があるときだけ**です。

## 10. ダメ出し検証

| 視点 | 想定される失敗 | 対策 |
|---|---|---|
| エンジニア | 直接デプロイ後に push を忘れ、次の誰かの push で変更が消える | 9章の手順6を必須にする。デプロイ当日中に push |
| エンジニア | `SHORT_SHA` を指定せずビルドが壊れる | 3章。`manualYYYYMMDD<英字>` を必ず付ける |
| エンジニア | 方法Bを常用し、イメージが2リポジトリに分散して本番の出所が分からなくなる | 常用は方法A。方法Bは緊急時のみ |
| 運用 | 権限が足りずデプロイ途中で止まり、中途半端な状態になる | Cloud Run は新リビジョンが Ready になるまで切り替わらないため、失敗しても現行は生き続けます。**途中で壊れることはありません** |
| 経営 | 手元から本番へ直接出せる状態が常態化し、レビューなしの変更が増える | 直接デプロイは「push できない事情があるとき」に限定。通常は GitHub 経由 |
| セキュリティ | 個人のgcloud認証で本番を触れる状態が残る | 作業後 `gcloud auth revoke` を検討。最低でも権限を持つアカウントを把握しておく |
| コスト | Cloud Build の実行が増える | E2_HIGHCPU_8・900s上限。1回あたり数分で、無料枠内に収まる規模です（**枠の残量は未確認**） |
