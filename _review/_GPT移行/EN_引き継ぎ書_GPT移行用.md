## 4. ブログの仕組み ― **最重要の落とし穴**【確定】

### 読み込みの優先順位
`blog/index.php` は次の順に読み、**同じIDは先に入ったほうだけを残します**。

```
① Firestore（news_find / news_published）   ← これが勝つ
② data/news.json
③ data/blog-posts.json
```

### つまり
**`data/blog-posts.json` を直しても、すでに Firestore にある記事には反映されません。**

`admin/migrate-blog.php` は「既存IDはスキップ」する仕様のためです。
`?force=1` は569件すべてを上書きし、管理画面での手直しも消すので**使用禁止**です。

### そこで用意した仕組み（v0272 で新規作成）
```
data/blog-sync.json        ← 上書きしたい記事IDのリスト
        ↓
/admin/sync-blog.php       ← 一覧を確認（上書きしない）
/admin/sync-blog.php?run=1 ← リストの記事だけを Firestore へ上書き
```
反映後は `blog-sync.json` の `ids` を `[]` に戻す運用です。

### 記事追加・修正の正しい手順
```
1. data/blog-posts.json を編集
2. 既存記事を直した場合は、そのIDを data/blog-sync.json に入れる
3. VERSION と config.php を上げる
4. git push（Cloud Build が走る）
5. /admin/migrate-blog.php  … 新規記事が入る（件数を確認・force禁止）
6. /admin/sync-blog.php     … 既存記事の修正が反映される
7. blog-sync.json の ids を [] に戻してコミット
```

### 記事データの形
`data/blog-posts.json` は `{"items":[...]}`。1件のキーは**この8つで固定**：
```json
{"id":"...", "date":"YYYY-MM-DD", "category":"...", "title":"...",
 "image":"/path/to.jpg", "body":"一覧用の要約", "body_html":"<p>本文HTML</p>", "published":true}
```
- 書き出しは `json.dumps(..., ensure_ascii=False, indent=1)` のあと `.replace('\n','\r\n')`

### 設計の肝
- **住所欄が出る条件は「資料請求にチェックが入っているか」の1本だけ**（以前は4通りあり、事故の原因だった）

- 任意項目には灰色の「任意」バッジ、必須には緑の「必須」バッジ
- 本文に「パンフレット送って」等の郵送希望ワードがあれば、住所欄を**任意で**開き、送信時に1回だけ確認して止める

| キー | 内容 |
|---|---|
| `category` | 選ばれたサービスを `／` で連結。「その他」に記入があれば `その他（◯◯）` |
| `shiryou` | 資料請求にチェックがあれば `"郵送を希望"` |

### 既存リンクとの互換
サイト内の資料請求CTA（`includes/shiryou-cta.php` ＝9ページ共通、ほか各サービスページ）は
`/contact/?service=資料請求（無料）` のままです。**1ページも書き換えていません。**
フォーム側で受けて、資料請求のチェックを入れる形にしてあります。
`?service=海洋葬` のようなサービス名は前方一致で該当チェックに入ります。

### PDFの配布
`/dl/?f=hakajimai&src=form` ／ `/dl/?f=checklist&src=form`
→ GA4 に `pdf_open` を送ってから PDF へ転送する中継ページ。`src=mail` と区別できます。

### 過去に起きた事故（再発防止のため記録）
1. **2026-09-13** … 都道府県を住所欄にプリフィルしていたため、「鹿児島県」だけで送信が通り、郵便番号の自動入力も効かなかった
2. **2026-11-04（小田様）** … 種別もガイドブックも選ばず本文に「パンフレットを、送付希望です」と書かれ、住所欄が一度も出ず発送できなかった
3. **同日発覚** … `#post-addr{...display:flex}` という**IDセレクタのCSSが hidden 属性に勝っていた**ため、2026年9月以降ずっとお届け先欄が表示されたままだった。しかも送信時に `hidden` で判定して `zip`/`addr` を削除していたため、**入力された住所が黙って捨てられていた**

> **教訓：`el.hidden === true` を見るだけでは不十分。`getBoundingClientRect().height === 0` で実際に画面から消えているかを見ること。**
> **検証ページを作るときは、ページ自身の `<style>` も必ず読み込むこと。** これを怠って2回見逃しました。

## 14. 作業の進め方（牧瀬様の標準ルール）

GPT に引き継ぐ場合、**この章をそのまま渡してください。**

### 回答の作法
- 日本語で、簡潔・断定的・行動指向に
- **確証のない情報は「未確認」と明記する。** 推測と事実を混同しない（数値・日付・固有名詞は特に厳密に）
- 嘘をつかない。わからない点は必ず尋ねる
- 否定的・印象の悪い言葉（「だめ」「絶望的」等）は使わない
- スコープの確認を求めず、**最大スコープの完全な提案を1回で出す**

### 回答の構成
1. 質問の背景推測（「推測」と明示）
2. 同感できる点
3. 批判する点（根拠付き）
4. リスクは「大きさ」と「起こる確率」を分ける
5. 次にとるべき一手を**一つだけ**
6. 別視点からのアドバイス
7. 自己検証
8. 末尾に「**この方針が外れていた場合の代替ルート**」を一つ

### Web改善の提案
必ず **【事実】【データ】【仮説】【変更内容】【期待効果】【リスク】【確認KPI】** をセットで書く。

**「GA4の数値が悪い→ページを変更」は禁止。** 次の順で進める：
```
数値異常 → 検索語句 → 流入チャネル → デバイス → 検索意図
→ 着地ページ → 実装確認 → 原因仮説 → 変更 → 再計測
```

### 成果物
- **報告は毎回 Markdown ファイル**で案件の docs/ に保存する。チャットの回答文そのものも MD に残す
- **チャットにファイルを添付しない**（容量圧迫を避ける）。明示的に求められたときだけ
- 重要案には「**この案が失敗するとしたら何が原因か**」のダメ出し検証を必ず付ける
- ユーザーの案に問題があるときは単純肯定せず、問題点・理由・リスク・改善案・代替案を提示

### デザイン
「AIっぽさ・テンプレ感」を避ける。写真主役・引き算・非対称のエディトリアルな組版。
