## 2. 前回提出資料からのさらなる訂正（ルール2を適用した結果）

「数値が悪い → 変更」ではなく実装まで遡った結果、前回資料の指摘のうち**3点が誤診**でした。

### 訂正4：スマホ固定CTAは「無い」のではなく「既に稼働している」

前回 P-14 で「電話・LINE・問い合わせの固定CTAは未設置」と書きましたが、誤りです。

`/assets/js/floating-cta.js`（8,187B）に、**閲覧段階に応じた出し分け機能が実装済み**でした。

| 設定値 | 値 | 意味 |
|---|---:|---|
| `PC_MIN_WIDTH` | 961 | 961px以上をPC扱い |
| `DISMISS_DAYS` | 7 | 閉じたら7日間出さない |
| `CLICKED_DAYS` | 30 | クリックしたら30日間出さない |
| `schedScroll` / `schedDwell` | 35% / 12秒 | 実施予定日バナーの表示条件 |
| `shindanPv` / `shindanDwell` / `shindanScroll` | **2PV** / 20秒 / 30% | 診断ナッジの表示条件 |
| `AB_ENABLED` | false | A/Bテストは無効 |

実機で `/kaiyou-sou/` を45%までスクロールし26秒待機したところ、`en-fcta en-fcta--schedule` が表示されました（高さ187px＝画面の15%）。

**つまり、ご指示の「何でも固定表示ではなく閲覧段階に合わせたCTA」は、すでに設計思想として実装されています。**
したがって今回必要なのは新規実装ではなく、**表示内容としきい値の見直し**です。

### 訂正5：フローティングCTAの中身が「電話・LINE・問い合わせ」ではない

実際に表示された内容：

```
× SCHEDULE
次回の合同海洋散骨  9月20日（日）  福岡博多湾
[ 予定日一覧を見る ]  → /kaiyou-sou/#goudou-schedule（同一ページ内アンカー）
```

- CTA枠という一等地が、**合同散骨の日程告知**に使われています
- リンク先は**同じページ内のアンカー**で、問い合わせ・電話・LINEには繋がりません
- `banner_impression` 64回 → `banner_click` 7回（**CTR 10.9%**）。仕組み自体は機能しています

### 訂正6：診断は「使われていない」のではなく「表示されていない」

前回 P-15 で「表示はされているが開始されない＝訴求文・設置位置の問題」と書きましたが、誤りです。

| 段階 | 回数 | 前段階からの到達率 |
|---|---:|---:|
| `shindan_nudge_show` | 32 | セッション1,991に対し **1.6%** |
| `shindan_start` | 13 | **40.6%** |
| `shindan_result` | 11 | 84.6% |
| `shindan_cta` | 7 | 63.6% |

**出れば4割が開始し、8割超が完走し、6割超がCTAを押しています。**訴求文にも設置位置にも問題はありません。

原因は表示条件です。診断ナッジは `shindanPv: 2`（**2ページ目以降**）を要求しています。
一方、実際のPV/セッションは広告経由で1.23〜2.16、自然検索も多くが1.0〜1.4。**大半のセッションが1PVで終わるため、そもそも表示条件を満たしていません。**

## 3. 改善提案（7ブロック形式）— 実装は承認後

### 提案1：フォームのボット対策強化とハニーポットの不可視化

| | 内容 |
|---|---|
| **【事実】** | `/contact/` の `generate_lead` は「Workerへの POST が成功 → looksHuman 判定通過」で発火する正しい実装。ボット対策は「ハニーポット `website`／経過時間5秒以上／メール正規表現」の3つのみで、reCAPTCHA・Turnstile は未導入。そのハニーポット `website` が画面に表示されている（幅26px×高さ45px、`display:block`／`visibility:visible`／`opacity:1`、`tabindex="-1"` のみ） |
| **【データ】** | 2026-08-01〜09-06（日本国内）：`generate_lead` 261回／148ユーザー。同期間の `form_start` 11回、`tel_click` 13回、`line_click` 10回。セッション1,991に対し `generate_lead` は13.1%。8/26は日本国内53セッションに対しCV43件、8/31は131セッションに対し46件 |
| **【仮説】** | 3点の弱い対策をボットが通過し、Workerが200を返し、フロントが成功扱いにしてCVを計上している。加えて、可視のハニーポットに実ユーザーが誤入力すると本物の問い合わせがスパム扱いになり、逆方向の取りこぼしも起きている |
| **【変更内容】** | ①ハニーポットを視覚的に完全非表示（`position:absolute; left:-9999px; width:1px; height:1px; opacity:0; pointer-events:none` ＋ `aria-hidden="true"`）②Cloudflare Turnstile を導入 ③Workerの応答に「受理したか」のフラグを持たせ、**受理時のみ** `generate_lead` を発火 ④`form_submit`（送信試行）と `form_error`（失敗）を追加 |
| **【期待効果】** | `generate_lead` が実問い合わせ件数と一致し、CVR・費用対効果の判断ができるようになる。誤入力によるスパム誤判定がなくなる |
| **【リスク】** | ①**CV数が見かけ上「激減」する**（改善なのに悪化に見える）→ 修正日を基準日として記録し、修正前後を別データとして扱う ②Turnstileが正規ユーザーを弾く可能性 → まず監視モードで1週間動かしブロック率を確認 ③イベント名 `generate_lead` は変更せず、過去データとの連続性を保つ |
| **【確認KPI】** | `generate_lead` の件数がBrevoの実受信数と一致するか（一致＝成功）／`form_start` → `form_submit` → `generate_lead` の到達率／Turnstileのブロック率 |
| **【前提】** | syu回答 Q1（8月の実問い合わせ件数）、Q2（Workerのスパム時の応答）、Q5（Turnstile導入可否） |
