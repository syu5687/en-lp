## 2. データモデル

```
コレクション : blog_likes
ドキュメントID: 記事ID（slug。例 teraumi-hiyou-wakare）
フィールド    : count      integer    累計いいね数
              updated_at timestamp  最終更新（サーバー時刻）
```

**個人情報は一切保存しません。** IP・UA・ユーザー識別子をFirestoreへ書いていません。二重押しの抑止はブラウザ側（localStorage）とCookieのみで行います。

## 3. コスト設計（frugal-cloud-architecture 準拠）

このスキルには「**『いいね』のようなPV連動の書き込み機能は原則作らない（作るならバッチ集約）**」という明確なルールがあります。今回は次の2点で趣旨を満たしています。

### 読み取り：PVに比例させない

記事ごとに読まず、**全件を1回まとめて読んでキャッシュ**します。

```php
en_cache('blog_like_counts', 1800, fn() => fs_list_all('blog_likes'))
```

- 読み取り試算：`いいねが付いた記事数 × (86400 ÷ 1800)` = 150記事なら **7,200/日**（無料枠 5万/日）
- 記事詳細・一覧・ランキングはすべてこの1つのキャッシュを使い回すため、**追加クエリは0**
- Firestore障害時は `try/catch` でいいね欄のみ非表示。ページは白紙になりません

### 書き込み：キャッシュを破棄しない（意図的な逸脱）

スキルには「保存・削除には必ず `en_cache_bust()` を対で入れる」とありますが、**いいねでは入れていません。**

理由：いいね1回ごとにキャッシュを破棄すると「いいね1回 → 次のPVで全件再読込」になり、**読み取りがいいね数に比例してしまう**ためです。代わりに、押した本人の画面はAPIの戻り値でJSが即時更新します。本人は常に正しい数を見ます（他の人には最大30分だけ古い数が出ます）。

管理画面はキャッシュを使わず生読みします（アクセス数が少ないため／スキルの方針どおり）。

### 書き込み量の上限

| 層 | 内容 |
|---|---|
| 1 | Cookie で同一ブラウザからの二重加算を抑止（書き込みを行わず現在値を返す） |
| 2 | インスタンス単位のトークンバケット：**分30回 / 日500回** |
| 3 | `BLOG_LIKE_ENABLED = false` で即停止 |

`cloudbuild.yaml` の `--max-instances=10` のため、最悪値は 500×10＝**5,000書き込み/日**。無料枠2万/日の範囲に収まります。

## 4. セキュリティ（公開APIのため多段）

| # | 対策 |
|---|---|
| 1 | POSTのみ・本文512バイトまで |
| 2 | 同一オリジン確認（`Sec-Fetch-Site`、無い環境は `Origin`/`Referer` で判定） |

| 8 | 件数は読み出し時に `max(0, …)` で負の値を丸める |
| 9 | Firestoreへの書き込みは Cloud Run のサービスアカウント経由のみ。ブラウザから直接Firestoreを触らない |

⚠ CSRFトークンは使えません（公開ページ・HTMLが300秒キャッシュされるため）。同一オリジン確認で代替しています。**いいねは不可逆な操作ではないため、この水準で妥当と判断しました。**

### ラベルについて（ご指示と違う判断をしたので明記します）

ご指示どおり**既定は「いいね」**にしました。ただし供養・終活の記事に「いいね」は軽く見える懸念があります。「兄弟で意見が合わない」「遺骨を押し付けられた」といった記事に「いいね 12」と出る違和感です。

`includes/config.php` の1行で切り替えられるようにしてあります。

```php
const BLOG_LIKE_LABEL = '参考になった';
```

ボタン上の見出しは「この記事は役に立ちましたか」としており、こちらは変更していません。

### この実装が失敗するとしたら

- **失敗要因①**：そもそも押されない。供養の記事を読む方は、SNS的な行動を取らない層が多い可能性があります。
  → 1か月で件数がほぼ0なら、**機能として失敗と判断して `BLOG_LIKE_ENABLED = false` にする**判断を持っておいてください。残すだけで保守対象が増えます。
- **失敗要因②**：GA4の記事別PVで足りていた。**「どの記事が読まれているか」はGA4で既に分かります。**いいねが足すのは「読んだ人が良いと感じたか」だけです。次に書く記事を決める目的なら、GA4のPVと滞在時間で判断できる可能性があります。
- **失敗要因③**：Firestore Security Rules が緩く、クライアントから `blog_likes` を直接書ける。**ルールの現状は未確認です。**クライアントからの読み書きが全拒否になっているか確認してください。
- **失敗要因④**：30分キャッシュのため、クライアント（堤様）が「押したのに数が増えない」と誤解する。管理画面は生読みなので、そちらで確認していただくよう伝えてください。
