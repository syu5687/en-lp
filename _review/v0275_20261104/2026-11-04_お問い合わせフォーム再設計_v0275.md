## 3. これで何が解決するか

### 3-1. 住所が取れない事故が構造的に起きなくなる

住所欄が出る条件は **「資料請求にチェックが入っているか」の1本だけ**になりました。

| | 旧（v0274まで） | 新（v0275） |
|---|---|---|
| 住所欄の条件 | 種別＝資料請求 **または**（ガイドブックON **かつ** 郵送ラジオ選択） | 資料請求のチェックのみ |
| お届け方法ラジオ | PDF／郵送の2択（条件を複雑にしていた） | 廃止 |
| 分岐の数 | 4通り | 2通り |

9月と11月に起きた2件の事故は、どちらもこの分岐の複雑さが原因でした。

### 3-2. 「資料を送りたいサービス」がはっきりする

旧：種別＝「資料請求（無料）」だけで、**何の資料を送ればいいか分からなかった**。
新：種別で選ばれたサービス（複数可）＋資料請求チェック、という形なので、
担当者通知に「お問い合わせ種別：お墓じまい／海洋葬（海洋散骨）」「資料請求（郵送）：郵送を希望」と並びます。

### 3-3. 複数サービスの相談を1件で拾える

「墓じまいをして、お骨は海へ」というご相談は実際に多いのに、
旧フォームでは種別を1つしか選べませんでした。

### 3-4. ガイドブックがその場で届く

メールが届かない方・迷惑メールに入る方にも確実にお渡しできます。
リンク先は `/dl/?f=...&src=form` の計測用中継ページなので、**GA4で `pdf_open` が取れます**
（`src=form` にしたので、メール経由 `src=mail` と区別できます）。

### 3-5. 入力の手間が減る

任意3項目（都道府県・年代・性別）を削除。選ぶ・考える箇所が3つ減ります。

## 4. 既存の仕組みを壊していないこと

### 4-1. サイト内の資料請求CTAはそのまま使えます

`includes/shiryou-cta.php`（9ページ共通）と各サービスページのCTAは
`/contact/?service=資料請求（無料）` のままです。**1ページも書き換えていません。**

JavaScript 側で受け皿を作りました。

| URL | 動き |
|---|---|
| `?service=資料請求（無料）` | 資料請求のチェックが入る（→お届け先が出る） |
| `?service=海洋葬` | 「海洋葬（海洋散骨）」にチェック（前方一致） |
| `?service=お墓じまい` | 「お墓じまい」にチェック |
| 一致しない値 | 「その他・まだ決まっていない」にチェック |

### 4-2. 「供養の選び方」診断からの遷移も従来どおり

`?shindan=` `?sdpath=` のバナー表示と通知メールへの記載は変えていません。

### 4-3. 担当者通知メールの項目

Worker の `FIELDS` から廃止3項目を外し、`資料請求（郵送）` を足しました。

```js
FIELDS: { name, kana, email, tel, category: "お問い合わせ種別",
          shiryou: "資料請求（郵送）", guides: "ご希望の資料（PDF）",
          zip, addr, goudou_date, shindan, … }
```

### 4-4. 自動返信の資料PDF送付

Worker の判定に `shiryou` を足しました。**旧フォームからの送信も拾えるよう、
`category` に「資料請求」が含まれる場合の判定も残しています。**

```js
const catShiryou = !!(d.category && String(d.category).includes("資料請求"))
                || !!String(d.shiryou || "").trim();
const wantsPost  = String(d.delivery || "").indexOf("郵送") >= 0
                || String(d.shiryou || "").indexOf("郵送") >= 0;
```

### 4-5. v0273・v0274 の修正は生きています

- 本文に「パンフレット送付希望」と書かれたら住所欄を**任意で開く**（v0273）

## 9. 自己検証

- **分岐を2通りに減らせたのが一番の成果**だと思っています。9月・11月の事故はどちらも「条件が4通りあって、どの組み合わせで住所欄が出るか追えない」ことが原因でした。機能を足して直すのではなく、**条件そのものを減らす**方向にできたのは、今回のご指示のおかげです。
- **既存の `?service=` リンクを1本も書き換えずに済ませた**のは意図的です。9ページ＋各サービスページを触ると、そこでまた別の事故が起きます。受け皿をフォーム側に1か所だけ作りました。
- **Worker の判定に旧 `category` の条件を残した**のも同じ理由です。デプロイの順番が前後しても壊れません。
- **送信後の後始末のバグは、スクリーンショットを撮っていなければ見逃していました。** 項目28は撮った画像を見て追加したものです。v0274 の反省（属性だけ見て画面を見ていなかった）が効きました。
- **管理画面DBへの `shiryou` 記録は見送りました。** `/api/inquiry-log.php` の受け口を確認していない状態で項目を足すと、保存が失敗する可能性があります。必要であれば次回に回します。

## この方針が外れていた場合の代替ルート

種別の必須化で離脱が増えた場合は、**必須をやめて「その他・まだ決まっていない」を初期チェック済みにする**のが次の手です。
選ばない方も進めるようになり、資料請求にチェックが入ったときだけ「どの資料をお送りしましょうか」と
その場で聞く形にできます。判断は `form_start` → `contact_submit` の到達率を2週間見てからです。
