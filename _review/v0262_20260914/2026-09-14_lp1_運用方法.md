# en1150｜`/lp1/` 運用方法

作成：2026-09-14 ／ 対象：https://en1150.co.jp/lp1/（`v2026091402`・本番公開中）
確認方法：本番HTML実測（Chrome MCP・Windows）＋ リポジトリ `D:\__github_win\en-lp\push\en-lp\lp1\`

---

## 0. 結論

**`/lp1/` は「広告専用の受け皿」として運用する。自然検索は `/kaiyou-sou/` に任せる。**

理由は3つ。

1. **いま `noindex` にしても失うものが無い。** `/lp1/` の公開は9/8。SEO資産の蓄積はまだほぼゼロ。あとから `index` に戻すのはいつでもできる（可逆）。逆に、両方を index のまま走らせて順位が割れてから戻すのは時間がかかります。
2. **`/lp1/` は「1ページで完結させて送信させる」設計。** 検索評価に必要な網羅性より、CV率を優先した構造です。SEOの主戦場にするなら別の作り込みが要ります。
3. **判定材料がまだ無い。** Search Console が未接続で、`/kaiyou-sou/` の実際の掲載順位・表示回数が **未確認**。この状態で「どちらをSEOの主にするか」を決めるのは、根拠の無い変更になります。

ただし、この判断には**反証もあります**（後述 11章「ダメ出し検証」）。3ヶ月後に再判定する前提で進めます。

## 2. 【S】いま決めて、いま実行すること

### S-1. `/lp1/` を `noindex,follow` にする

**【事実】** 現在 `/lp1/` は `index,follow,max-image-preview:large`、canonical は自己参照。
title「鹿児島・錦江湾の海洋散骨｜粉骨から供養まで｜有限会社 縁」、h1「鹿児島の海に、大切な想いを。」。
`/kaiyou-sou/` と検索意図が完全に重なります。

**【データ】** 2026/8/1〜9/6（国内）で `/kaiyou-sou/` は広告146セッション（EG54.1%）に対し**自然検索5セッション**。
自然検索の主力は `/powder/`（30・EG90.0%）と `/grave/`（21・EG71.4%）。
「鹿児島 散骨」系の広告流入は28セッション・EG60.7%で、商圏本命。

**【仮説】** 同一サイト内で同一意図のページが2枚あると、Googleがどちらを出すか揺れ、
`/kaiyou-sou/` の評価が分散する。いまの `/kaiyou-sou/` の自然流入は小さいが、
**その順位が「元々低い」のか「まだ計測していないだけ」かは未確認**。分散させてから確かめるのは順序が逆です。

**【変更内容】** `lp1/index.php` の robots メタを `noindex,follow` に変更。
`follow` を残すのは、LPから既存ページへのリンク評価を止めないため。canonical はそのまま。

**【期待効果】** `/kaiyou-sou/` の自然検索評価を守りつつ、広告の受け皿としての `/lp1/` を自由に試せる。

**【リスク】** `/lp1/` 経由の自然流入はゼロになります。ただし公開6日でほぼ実績が無いため、失うものは限定的。

**【確認KPI】** Search Console：`/kaiyou-sou/` の平均掲載順位・表示回数（noindex適用の前後で比較）。

### S-2. `/lp1/` の送信を `contact_submit` でも計測する

**【事実】** 本体フォーム（`/contact/`）は v0258 で `contact_submit` を新設し、**送信数はこれを見る**運用に変更済み。
一方 `/lp1/` は `lp1/script.js` で `generate_lead`（`form_name: 'lp1_kagoshima_ocean_burial'`）しか送っていません。

**【データ】** 2026年8月のGA4で `generate_lead` は261件。ハニーポットが 26×45px で可視・Turnstile 未導入のため、
**スパム疑いと判定済み**（9/7解析）。`generate_lead` は現状「汚れた指標」です。

**【仮説】** このままLPへ広告を流すと、LPのCVがスパムに埋もれ、**LPの勝敗を判定できません。**
「滞在時間が伸びた」だけで判断することになり、これは禁止している進め方です。

**【変更内容】** `lp1/script.js` の送信成功ブロックに `contact_submit` を追加。`generate_lead` は**残す**（既存イベント名を変更しない）。

```js
gtag('event', 'contact_submit', {
  form_name: 'lp1_kagoshima_ocean_burial',
  category: data.category || '(未選択)',
  method: 'inline_form'
});
```

**【期待効果】** 本体フォームとLPフォームを同一指標で並べられ、広告の最終URL切替の可否をCVで判断できる。

**【リスク】** 低。イベント追加のみ。GA4側で `form_name` をカスタムディメンション登録する作業が別途必要。

**【確認KPI】** `contact_submit`（`form_name=lp1_kagoshima_ocean_burial`）の件数と、Brevo受信の実件数の一致。

### S-3. 広告クリックの出所を送信データに残す

**【事実】** `lp1/script.js` は `source: location.href` を送っていますが、
**`gclid` / `utm_*` を独立した項目として保存していません。** フォームに hidden も無し（実測：hidden 0個）。

**【仮説】** 問い合わせが来ても「どのキャンペーン・どの検索語句から来たか」が管理画面側で追えない。
広告の予算配分を決めるときに、GA4の推計しか根拠が無くなります。

**【変更内容】** 送信データに以下を追加（`URLSearchParams` から取得、無ければ空）。

```
gclid / utm_source / utm_medium / utm_campaign / utm_content / utm_term / landing_page（= '/lp1/'）
```

Worker（`worker/en-contact/worker.js`）→ 管理画面DB へそのまま保存。

**【期待効果】** 「このキャンペーンから実際に何件の問い合わせが来たか」を、GA4とは独立した実データで確認できる。

**【リスク】** Worker とDBのスキーマ追加が必要。既存項目は触らない前提で追加のみ。

**【確認KPI】** 管理画面の問い合わせ一覧に `landing_page=/lp1/` の行が出ること。

### S-4. 合同散骨の日程が「手打ち」であることの運用ルール化

**【事実】** `/lp1/` の日程セクションは **`2026年 10月24日（土）` がHTMLに直接書かれています。**
`/kaiyou-sou/#goudou-schedule` への「今後の開催予定を見る」リンクはありますが、LP内の日付は自動更新されません。

**【データ】** 確定している開催予定：9/20(日)福岡 ／ **10/24(土)鹿児島** ／ 11/15(日)福岡 ／ 12/19(土)鹿児島。

**【仮説】** 10/25以降、LPは**終わった日程を表示し続けます。**
「次回開催予定」と書かれた下に過去の日付がある状態は、信頼性を直接損ないます。

**【変更内容】** 2案。

- 案A（推奨・低工数）：**更新日をカレンダーに固定**する。`10/25` と `12/20` に「LP日程更新」のタスクを入れる。
  次回が未定の期間は「次回開催日は現在調整中です」に差し替え（確定済みの表記ルール）。
- 案B（根治・要工数）：日程を `includes/` 側のデータに寄せ、`/kaiyou-sou/` と `/lp1/` が同じ値を読む。二重管理をなくす。

**【期待効果】** 「日付が古い」というLPで最も致命的な事故を防ぐ。

**【リスク】** 案Aは人が忘れると事故ります。案Bは既存ページの日程表示に触るため、影響範囲の確認が必要。

**【確認KPI】** 毎月1日のチェックで、LP表示日付 ≧ 当日 であること。

## 3. 【S】広告の流し方 — いきなり100%は流さない

**【事実】** 現在 `/kaiyou-sou/` が鹿児島・海洋散骨の広告の受け皿（146セッション・EG54.1%）。
`/lp1/` はまだ広告流入ゼロ（広告管理画面での最終URL変更が未実施のため）。

**【変更内容】** 3段階で切り替えます。

| 段階 | 配分 | 期間 | 次へ進む条件 |
|---|---|---|---|
| 第1段階 | `/lp1/` 30%・`/kaiyou-sou/` 70% | 2週間 | CV数が母数に達する（合計CV 10件以上） |
| 第2段階 | 50/50 | 2週間 | `/lp1/` のCPAが `/kaiyou-sou/` 以下 |
| 第3段階 | `/lp1/` 100% | — | 第2段階をクリア |

**判定基準は CV数 と CPA。** エンゲージメント率・滞在時間だけで勝敗を決めません。
LP型ページは1ページ完結のため、回遊型の `/kaiyou-sou/` とは PV/セッション の意味が違います。

**補助指標（原因究明用）**：スクロール深度、`#contact-form-section` 到達率、`tel_click`、`line_click`、フォーム離脱位置。

**【前提】** S-2（`contact_submit`）が入っていないと、この判定はできません。**S-2 → 広告切替 の順序を守ります。**

**【リスク】** 第1段階でCVが集まらないと判定期間が延びます。CV10件に届かない場合は、期間で切らず母数で待ちます。

## 4. 【A】LP内の導線を整理する

### 4-1. 外部リンク12本の扱い

**【事実】** `/lp1/` からサイト内の他ページへ **12本のリンク**があります。
`/kaiyou-sou/`・`/powder-cleaning/`（2本）・`/teraumi/`・`/temoto-kuyou/`・`/staff/`・`/voice/`・`/company/`・`/blog/`・`/policy/`・`/privacy/`。

**【仮説】** 信頼を補強する役割（スタッフ・お客様の声・会社概要）と、**LPから離脱させる役割**が混在しています。
とくに日程の「今後の開催予定を見る 〉」は `/kaiyou-sou/` へ飛ばすため、**検討が最も進んだ瞬間にLPを離れます。**

**【変更内容】** 段階的に。まず計測から。

1. 各外部リンクに GA4 の `outbound_internal`（新規イベント／既存名は変更しない）を付け、**どこから抜けているか**を1ヶ月測る
2. 離脱の多いリンクだけ、`target="_blank"` へ変更するか、LP内に内容を取り込む
3. 日程リンクは、LP内に「今後の開催予定」を3件まで直接表示する案を検討（S-4案Bと同時実施が効率的）

**【確認KPI】** `outbound_internal` の発火数、フォーム到達率の前後比較。

### 4-2. 固定CTA（`floating-cta.js`）を入れるかどうか

**【事実】** `/lp1/` は `includes/footer.php` を読み込んでおらず、`floating-cta.js` も未読込。
LP専用フッターのみ。ページ内には 電話4本・LINE3本・フォームアンカー7本 があります。

**【仮説】** LP内にCTAが14箇所あるため、**固定CTAが無くても導線は足りている可能性があります。**
ただしスマホで実際にスクロールしたときの到達性は **未検証**。

**【変更内容】** 先に実機（スマホ）でスクロールし、「CTAが画面から消えている区間」が何秒あるかを確認。
長い区間があれば、**新しいCTAシステムは作らず `floating-cta.js` を流用**します（イベント名 `banner_impression` / `banner_click` / `banner_dismiss` / `shindan_nudge_show` は変更禁止）。

**【リスク】** 固定CTAはスマホで本文を隠します。入れる場合はLPの余白設計に合わせた調整が要ります。

## 5. 【A】スパム対策 — LPのCVを守る前提条件

**【事実】** ハニーポット `website` は `class="hp-field"` で実装済みですが、**本体側で 26×45px で可視**と判定済み（9/7）。
Turnstile は未導入。`lp1/script.js` の人間判定は `elapsedMs >= 5000 && !data.website` のみ（**GA4送信の抑制だけ。フォーム送信自体は止まりません**）。

**【データ】** 2026年8月 `generate_lead` 261件がスパム疑い。同月GA4はシンガポールからのボットが2,811中1,255（44.6%）。

**【仮説】** LPに広告を流すと、URLが露出してボットの標的になります。**CVが汚れると3章の判定が成立しません。**

**【変更内容】**
1. ハニーポットを完全不可視に（`position:absolute; left:-9999px; width:1px; height:1px; opacity:0` ＋ `tabindex="-1"`・`autocomplete="off"` は既に有り）
2. Cloudflare Turnstile を Worker 側で検証（**キーの発行可否をsyuに確認**）
3. Worker 側でレート制限（同一IP・同一メールの短時間連投を弾く）

**【リスク】** Turnstile は正規ユーザーの離脱要因になり得ます。まず1と3を入れ、効果が足りない場合に2を判断。

**【確認KPI】** `contact_submit` と Brevo実受信の乖離、管理画面DBの重複・不自然な送信の件数。

## 6. リリース手順（毎回これを守る）

1. `git pull --ff-only origin main`
2. `lp1/` の対象ファイルだけ編集
3. **バージョンを3箇所そろえる** — `lp1/index.php` のReleaseコメント／`<meta name="version">`／CSS・JSのキャッシュキー（`?v=`）
4. PC幅・スマホ幅で表示確認（横スクロール・文字切れ・CTAの被りが無いこと）
5. 対象ファイルのみコミット → `main` へ push
6. Cloud Build の完了を待つ
7. `https://en1150.co.jp/lp1/?cb=<新バージョン>` を開き、version・文言・画像・フォーム送信・PC/SP表示を確認
8. 変更点・未確認事項・確認結果を `.md` で `_review/` へ保存

⚠ **このセッションから端末のgit操作はできません**（シェル未接続／ロックファイル問題）。
git は syu または Codex 側で実行してください。Claude側はファイルの読み取りと書き戻しまでです。

⚠ **本番の送信テストはGA4キーイベントとGoogle広告CVに1件入ります。**
`en_nt` クッキー（管理画面に入ったことのある端末）があればGA4タグは出力されません。テスト前に管理画面へ一度ログインしておきます。

## 8. 福岡版（`/lp2/` 等）を作るかの判断

**【データ】** 福岡圏の広告流入37セッション・EG59.5%。そのうち
「和布刈神社散骨」8＋「めかり神社散骨費用」4＋「関門海峡散骨」2＋「下関散骨センター」2 ＝ **16セッション（43%）**が
**具体的な散骨スポット名**の検索で、一般語の「散骨 福岡」（5）を大きく上回っています。

**【制約】** 「関門海峡」「北九州」「下関」は **syuの確認が取れるまで記載禁止**。和布刈神社の名称を使ったSEOページも**作らない**。

**【現状の判断】** **この制約が解けるまで、福岡版LPは作りません。**
最大の勝ち筋KWが使えない状態で作っても、`/kaiyou-sou/fukuoka/`（EG45.3%）や `/fukuoka/`（EG69.7%）と役割が重なるだけです。

**【先に打てる手】** 福岡は**新規LPではなく既存ページの活用**で対応。
広告の遷移先を `/fukuoka/`（EG69.7%）に寄せるA/Bテストが、工数ゼロで効果検証できます。

**【解禁されたら】** `/lp1/` と同じ構成で、実写・料金・出航地（姪浜旅客待合所）を福岡のものに差し替えて展開。
